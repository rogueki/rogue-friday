# P9 task creation action slice

Current boundary: the task dialog and `/commands` task-create path use the captured preview and approval policy. Direct API `POST /api/v1/tasks` still uses the existing Tasks port and can create a task without this native preview; universal enforcement across all task-create entrypoints is open and must be completed before claiming the policy applies globally.

The task dialog and explicit text commands now use the same Control API command handler. The handler parses a task-creation request, persists a scoped draft and its approval terms, returns a preview, then requires the saved `previewId` and unchanged action on confirmation. Dismissing the preview cancels the server draft; a stale confirmation cannot revive it. The native approval appears in the existing `/approvals` list and detail routes. The existing token, role, expiry, session and version checks run before a decision; successful approval calls the configured Tasks port with a stable idempotency key and saves a task receipt. If tier-2 approval is disabled, the explicit preview confirmation calls that same port once and saves a receipt. Nothing is sent to an external account by this action.

`NativeApprovalRequests` is the shared persistence seam in `apps/control-api/src/services/native-approval-requests.ts`. A new family adds a discriminated `NativeExecutableAction` kind, validates and persists an exact payload, then adds a dispatch branch to `handlers/approvals.ts`. Its UI and text entrypoints should call one domain action handler, as task creation does in `handlers/commands.ts`. Migration 21 owns this table; the producer keys are scoped by authenticated owner ID. The dev scenario reset clears only synthetic native requests so isolated browser tests do not inherit prior approvals.

Before calling the Tasks port, the API atomically records the decision and a dispatch token. A failed or timed-out call leaves the action `uncertain`; a restart or repeated click cannot resend it. Late responses may save a receipt only with the matching token. The key is forwarded to Hermes, but the deployed Hermes server's durable deduplication has not been verified, so the API does not rely on that key for automatic retries. An uncertain result requires operator reconciliation against the actual task board before any new action. A crash during dispatch remains visible as an approved action with unconfirmed execution. This is an at-most-once dispatch rule, not proof of exactly-once remote execution.

Validation: focused Control API tests (five files, 59 tests) passed; Control API and Web typechecks and `pnpm build:app` passed. Four Windows Playwright Task tests passed, including UI preview followed by direct task creation when tier-2 approval is disabled, UI preview followed by native approval and a single task receipt with the default policy, and dismissal without an action. Ten distinct creation phrasings and negative/read-only phrases are tested. Tests used mock adapters and synthetic data. A real Hermes Kanban round trip, broader task actions, correction across separate pending drafts, and a live restart during dispatch remain unverified or unimplemented; this slice does not complete all P9 families.
