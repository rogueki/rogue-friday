# P9 calendar action family slice

The calendar mutation family (create / update / delete of Friday-local events) now runs through the same native staged pipeline as the task family — no contract or OpenAPI change was needed. Direct API `POST /api/v1/calendar/local/events`, `PUT …/{id}` and `DELETE …/{id}` stage the exact write first: the initial request answers `403 APPROVAL_REQUIRED` with `stage: preview`, a `previewId` and a German `previewText`; the repeat must carry the unchanged action plus `X-Action-Preview-Id`. Under the captured tier-2 policy the confirmed request either returns `stage: approval` with an approval ID for the existing list/detail/decision UI, or executes once and returns the receipt (201/200) when approval is disabled. A replayed confirmation returns the stored receipt without a second write; because the delete draft carries a full event snapshot, a replayed delete confirmation still answers with the deleted event after it is gone. One Idempotency-Key spans staging and confirmation (the preview error is never cached); a mismatched body under the same key still fails 409. Guards run before anything is staged: an invalid body answers 422, an unknown event 404, a missing If-Match 422 and a stale version 409 — none of them leaves a draft behind. There is deliberately no capability check: the route declares `capability: null` because the local calendar is Friday's own database, not an adapter port.

The command path parses German calendar intents in `services/calendar-action-intent.ts`: creates ("Trage Quartalsplanung morgen 14 Uhr ein", "Plane Zahnarzt am 24.10. um 8 Uhr", …), moves ("Verschieb den Termin Sprintreview auf Freitag 10 Uhr", …) and deletes ("Lösche den Termin …", "Sag den Termin … ab", …). Relative dates resolve against `runtime.nowMs()` — the deterministic clock seam (the mock world's controllable clock in tests) — in the profile timezone, with a DST-corrected zone conversion; a phrase without an explicit clock time is never treated as a scheduling instruction. Extracted titles keep their original spelling while keyword matching is case- and umlaut-insensitive. The reference is an event id or an exact unique local title; phrases without one resolve the single selected event of the existing command `context.selectedIds`. Resolution happens before staging: an unknown title answers 404, an ambiguous title 409 ("Mehrere Termine passen …"), a missing or plural selection 422. Moves keep the event's duration. Dismissing the preview cancels the server draft; a stale confirmation cannot revive it. Because update/delete embed the target version in the stored action, a repeated command confirmation after a successful move or delete re-resolves to a new version and fails 409 instead of writing twice — exact-body binding beats silent replay there, while command creates and all direct-API replays return the stored receipt.

`NativeExecutableAction` gained the `calendar.create` / `calendar.update` / `calendar.delete` kinds in `services/native-approval-requests.ts`; the receipt sentence is subject-aware ("Aufgabe … angelegt." stays byte-identical, "Termin cal_… eingetragen./aktualisiert./geloescht." is new), and a new read-only `readAction` accessor lets a replayed delete confirmation answer from the stored snapshot. `handlers/approvals.ts` dispatches the three kinds through `LocalCalendarService` on the owner's database. The atomic decision+dispatch-token and `uncertain` semantics are unchanged: a calendar dispatch that fails after the decision leaves the action `uncertain` and cannot be re-sent (covered by a service-level test). The dev scenario reset clears the whole `native_approval_requests` table, which covers the new kinds (tested).

Web: the staged-write runner was generalized instead of copied. `apps/web/src/lib/api/stagedWrite.tsx` holds the shared Zustand store, `useRunStagedWrite()` and `StagedWriteConfirmHost`; the write's full request (body, If-Match, idempotency key) is captured in a send closure so a confirmation can never alter what was previewed, and the hook reports `executed | preview | approval | failed` so callers can decide whether to keep an editor open. `features/tasks/taskWriteRunner.tsx` is now a thin wrapper that keeps the `useRunTaskWrite` / `useTaskWriteBusy` / `TaskWriteConfirmHost` exports (the tasks suite is unchanged and green). `features/calendar/LocalEventDialog.tsx` saves and deletes through the runner; the inline delete-confirmation group was removed — the server preview is the single confirmation, as on the task drawer. A pre-staging validation error keeps the dialog open with an inline alert; a staged, queued or executed write closes it.

Validation: baseline before the changes — the focused calendar/command/approval files (`local-calendar`, `voice-calendar`, `caldav-create`, `native-task-action`, `native-task-status-cancel`, `task-action-intent`, `task-create-intent`, `approvals`) passed 88 tests. After the changes: new `calendar-action-intent` suite 28/28 (16 distinct action phrasings across create/move/delete plus 12 negative or unresolvable phrases, including the DST transition at 2026-10-25), new `native-calendar-action` suite 9/9 (spoken create through approval, spoken move with duration kept and replay-409, delete via `selectedIds` with dismiss semantics, pre-staging 404/409 without drafts, direct-API staging with approval and receipt, If-Match guards with update/delete receipts and snapshot replay, one idempotency key across staging and confirmation, uncertain-dispatch without resend, dev-reset consistency), the migrated `local-calendar` API test now drives the staged flow (125 passed in the combined focused run of ten files). Full Control API suite: 94 files, 714 passed, 1 pre-existing skip, twice in a row; full web suite 71 files / 603 passed; API and web typechecks pass; ESLint on all changed files is clean; `git diff --check` is clean; `pnpm contracts:check` was not needed (no contract file touched); `pnpm build:app` succeeded. Playwright on Windows against the real gated mock stack: `tests/e2e/tasks.spec.ts` 4/4, `tests/e2e/command-bar.spec.ts` 6/6 and `tests/e2e/a11y.spec.ts` 35/36 in the combined run — the single a11y failure (`keyboard › the whole task flow`, palette ArrowDown landed on a memory result instead of the tasks navigation, before any write path was reached) is unrelated to this slice and passes on the isolated rerun; no calendar-specific E2E spec exists, so there was nothing to repair there.

Still unverified or out of scope: CalDAV/connected-provider writes remain on their own adapter path and were not moved onto this pipeline; the command path parses only create/move/delete (no attendee, location or recurrence edits); a live restart during a calendar dispatch and a cross-owner replay of a preview ID remain unverified; the other P9 families (mail, messaging, …) are untouched. Receipt replays that reach the handler again (instead of the idempotency cache) are stamped `Idempotent-Replayed: false` by the pipeline, matching the task family.
