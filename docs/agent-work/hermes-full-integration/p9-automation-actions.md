# P9 automation action family slice

The automation mutation family (create / update / enable / disable / test / pause-all) now runs through the same native staged pipeline as the task, calendar, mail, messenger, agent and file/knowledge families — no contract or OpenAPI change was needed. `POST /api/v1/automations`, `PATCH /api/v1/automations/{id}`, `POST /api/v1/automations/{id}/enable`, `POST /api/v1/automations/{id}/disable`, `POST /api/v1/automations/{id}/test` and `POST /api/v1/automations/pause-all` stage the exact write first: the initial request answers `403 APPROVAL_REQUIRED` with `stage: preview`, a `previewId` and a German `previewText`; the repeat must carry the unchanged body plus `X-Action-Preview-Id`. Under the captured tier-2 policy the confirmed request either returns `stage: approval` with an approval ID for the existing decision UI, or executes exactly once and answers the entity, the run, or the per-automation pause result. A replayed confirmation answers the stored receipt without a second port call: re-fetch of the entity for create/update/enable/disable, the recorded run for a test, and the current per-automation pause state for pause-all (the outcome there is derived state, so the replay re-derives `skipped`/`already_paused`/`paused` from the live list instead of inventing a second bulk write).

Guards run before anything is staged: unknown automations fail 404; a stale `If-Match` fails 409 before staging (the staged draft pins the seen version and the port re-checks it at dispatch, so a replayed confirmation after a concurrent write fails 409 instead of overwriting newer state); an invalid cron expression or an event trigger without an event fails 422; a missing capability (`automations.create`/`update`/`enable`/`disable`/`test`/`pauseAll`) fails 403 `CAPABILITY_MISSING`; an invalid `X-Action-Preview-Id` shape fails 422. None of them leaves a draft behind (asserted against `native_approval_requests`). The confirmation binds the exact stored action: a tampered repeat body fails 409.

`NativeExecutableAction` gained the kinds `automation.create` (exact `AutomationCreateRequest`), `automation.update` (id, pinned version, exact `AutomationUpdateRequest` — which is also how pause/resume are expressed), `automation.enable` / `automation.disable` (id, pinned version), `automation.test` (id, exact `AutomationTestRequest` including `dryRun` and the sample data) and `automation.pauseAll` (exact `AutomationPauseAllRequest`) in `services/native-approval-requests.ts`; the receipt sentences are `Automation <id> angelegt./aktualisiert./aktiviert./deaktiviert./getestet.` and `Automationen <pausedCount> pausiert.`. `handlers/approvals.ts` dispatches all six kinds on the decision's own idempotency key through one shared `dispatchAutomationAction` in `handlers/automation-actions.ts`, which the direct API handlers and the command path also use. The preview texts are deliberately concrete about side effects: a real test run says that it executes the actions and triggers tasks, notifications and approvals, a dry run says that conditions are checked and nothing is executed, and a redundant enable/disable says the automation already is in that state. The dev scenario reset clears staged automation drafts like every other family (tested: a confirmation after the reset fails 409).

The command path parses German automation intents in `services/automation-action-intent.ts`: enable ("Aktiviere/Schalte … ein"), disable ("Deaktiviere/Schalte … ab"), pause ("Pausiere …", "Halte … an", "Leg … still"), resume ("Setz … fort", "Lass … weiterlaufen"), test ("Teste/Probiere … aus") and pause-all ("Pausiere alle Automationen", "Stoppe/Halte an/Leg still alle Automationen"). Only explicit imperatives that name an `Automation`/`Automationen` are treated as actions, and the reference is resolved before anything is staged: an `auto_…` id directly, an exact unique name via the live automation list, or the single selected automation of the command context; unknown references fail 404, ambiguous ones fail 409 instead of guessing. Creating an automation through language stays out of scope on purpose — it needs a structured trigger/condition/action definition that a spoken sentence must not invent. A paused or disabled target is accepted with an honest preview („ist bereits pausiert — trotzdem erneut setzen?“) instead of a silently ignored write.

Frontend: `AutomationsPage` enable/disable, pause-all and the per-target resume loop run on `useRunStagedWrite`; `TestPanel` stages the dry run (the sample JSON is bound by the stored draft, so a confirmation can never execute a different sample than the previewed one); the global command palette starts a real run through the same runner, so the write is confirmed twice by design — the palette's own preview plus the server preview. The former page-local pause-all confirmation and the direct `useTestAutomation` mutation are gone; every write path now shares one confirmation host, one busy state and one invalidation set. `automations.test.tsx` drives the staged protocol (403 with `stage: preview`, then the repeat with `X-Action-Preview-Id`) for pause-all and resume and asserts that no `PATCH` fan-out happens for pausing.

Verification: `pnpm --filter @friday/control-api typecheck`, `pnpm --filter @friday/web typecheck`, `pnpm lint` (0 errors), `pnpm contracts:check`, `pnpm build:app` and `pnpm test:conformance` (415 passed, 60 skipped) are clean; the full local suite ran 245 files / 3368 passed / 61 skipped, and the focused API run `native-automation-action.test.ts` + `automation-action-intent.test.ts` + `contract.test.ts` + `contract-gaps.test.ts` passed 109 tests. The seven native tests cover create with replay, tamper and version drift on update, enable/disable with pre-staging guards and one tier-2 approval, dry run plus real run recording exactly one entry each, pause-all with its replay, the spoken command path including live-registry resolution, and the reset.

Limits: the mock port proves staged pipeline semantics, not real scheduler effects — whether a paused automation actually stops firing, whether a test run really triggers downstream tasks/notifications/approvals, and whether the cron/timezone semantics hold is **NOT_RUN** against a live Hermes scheduler; provider-backed notification effects of a test run stay unproven; the approval-path dispatch writes no durable-memory capture event for the automation family (unlike mail/messenger sends); a live restart during a dispatch and a cross-owner replay of a preview id remain unverified like in the sibling families; spoken references match exact names/ids only (no fuzzy matching), and spoken automation creation is not implemented by design.
