# P9 task status change and cancel action slice

Direct API `PATCH /api/v1/tasks/{id}` and `POST /api/v1/tasks/{id}/cancel` now enforce the same policy as task creation. The first request returns `403 APPROVAL_REQUIRED` with `stage: preview` and a `previewId`; the client must repeat the exact body with `X-Action-Preview-Id`. Under the captured tier-2 policy the second request either returns `stage: approval` with an approval ID for the existing list/detail/decision UI, or executes once and returns the task receipt (200) when approval is disabled. A replayed confirmation returns the stored receipt without a second write. The `cancelTask` operation accepts an Idempotency-Key and behaves like task create (the preview error is not cached, one key spans staging and confirmation); the contract declares no Idempotency-Key header for `updateTask`, so the pipeline ignores one there — staging and confirmation are bound by the preview ID alone.

The command path parses German status changes ("Markiere die Aufgabe X als erledigt", "Setze den Task X auf in Arbeit", …) and cancels ("Lösche die Aufgabe X", "Storniere den Task …", "Brich die Aufgabe X ab", …) in `services/task-action-intent.ts`. The reference is a task id or an exact unique title; phrases without a reference resolve the single selected task of the existing command `context.selectedIds` — no new dialog-context subsystem. Resolution happens before anything is staged: an unknown title answers 404, an ambiguous title 409, a missing or plural selection 422, a cancel of an already finished task 409, and a schema-invalid status 422 — none of them leaves a draft behind. Confirmation re-resolves the reference and must reproduce the stored action exactly, so a renamed task or a changed status phrase fails with 409 instead of reviving or altering the draft. Dismissing the preview cancels the server draft; a stale confirmation cannot revive it. Preview texts are distinct per action ("… auf review setzen?", "… als Erledigt markieren?", "… abbrechen?").

`NativeExecutableAction` gained the `task.update` and `task.cancel` kinds in `services/native-approval-requests.ts`; the receipt sentence is kind-aware ("angelegt" / "aktualisiert" / "abgebrochen"). `handlers/approvals.ts` dispatches all three kinds through the existing Tasks port (`createTask` / `updateTask` / `cancelTask`, both already present on the mock and Hermes adapters — no port seam was added). The approval decision's own If-Match guards the approval version and is deliberately not forwarded as the task version in this dispatch path; the direct API path forwards If-Match to the task write, so optimistic-concurrency semantics (current version applies, stale/quoted/weak values behave as before, `*` and a missing header mean no precondition) hold through the confirmation. The atomic decision+dispatch-token and `uncertain` semantics are unchanged: a failed or timed-out update/cancel dispatch leaves the action `uncertain`, cannot be re-sent by a repeat, and a late receipt is only saved with the matching token. The dev scenario reset clears the whole `native_approval_requests` table, which covers the new kinds.

Web UI follow-up (correction round): the browser flow now speaks the staged protocol everywhere the gated writes surface. A new `apps/web/src/features/tasks/taskWriteRunner.tsx` holds a small Zustand store for the pending staged write, a `useRunTaskWrite()` hook that sends the first request, opens a confirm dialog with the server `previewText` on `stage: preview`, resends the unchanged body with `X-Action-Preview-Id` on confirm, shows an amber approval toast with a link to `/approvals?approval=…` on `stage: approval`, and refetches tasks on `CONFLICT`. `TaskWriteConfirmHost` is mounted once in `AppShell` next to `CommandConfirmHost`. `useTaskCommands` routes Kanban moves, the drawer cancel, "approve result" and the assign-via-update fallback (adapters without `agents.assignTask`) through this runner; pause/resume/retry and `POST /tasks/{id}/assign` stay one-shot adapter actions. The obsolete one-shot `useUpdateTask` hook and the `"cancel"` variant of `useTaskAction` were removed from `lib/api/domains/tasks.ts`, and the drawer's own cancel confirmation dialog was deleted — the server preview is now the single confirmation. Nothing is patched optimistically anymore: the board changes only when the server executed the write. Dismissing the preview dialog only closes it client-side (the direct-API flow has no draft-cancel endpoint, unlike the command path); the orphaned draft is keyed by its preview ID, invisible and harmless. A double-staged action creates two drafts; only the matching preview ID plus the exact body confirms.
