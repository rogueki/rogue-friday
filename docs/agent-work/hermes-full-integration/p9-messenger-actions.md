# P9 messenger action family slice

Plain outbound messenger sends now run through the same native staged pipeline as the task, calendar and mail families — no contract or OpenAPI change was needed. `POST /api/v1/messenger/confirm` splits by draft shape: an escalation draft (`notificationId`/`notificationStep`) keeps the existing stage/token flow against `notification_messenger_stages` untouched, while a plain send stages the exact write first — the initial confirm answers `403 APPROVAL_REQUIRED` with `stage: preview`, a `previewId` and a German `previewText` (`Nachricht über <platform> an <recipient> senden? Text: „<capped summary>“`); the repeat must carry the unchanged draft plus `X-Action-Preview-Id`. Under the captured tier-2 policy the confirmed request either returns `stage: approval` with an approval ID for the existing approval UI, or executes once when approval is disabled. `NativeExecutableAction` gained the `messenger.send` kind (receipt sentence `Nachricht <receiptId> versendet.`), and `handlers/approvals.ts` dispatches it through `MessengerSendService.sendStaged`.

Sends keep their at-most-once guarantee through the existing `messenger_send_journal`: the journal key of a staged send derives from the preview id (`native-action:<owner>:<previewId>` for direct confirms, `native-approval:<approvalId>` for approval decisions), so confirmation, approval and replay land on the same durable reservation with the draft-hash replay check and the boot-time pending→uncertain sweep unchanged. A replayed confirmation returns the stored receipt with `Idempotent-Replayed: true` and `replayed: true` without a second gateway attempt; an uncertain gateway outcome is answered as `uncertain` on every replay and never re-sent. `MessengerSendService` grew the seams for this: `checkedMessengerDraft` (validate-only), `assertSendable` (target admission plus live readiness probe without touching the journal), `sendStaged` (token-free send for the native pipeline; the staged draft and its exact-body confirmation replace the preview token, while admission check, readiness re-check and journal stay identical) and `receipt` (journal state for a known receipt, owner-checked).

Resolution honesty runs before anything is staged: an invalid draft answers 422, an unregistered recipient 422 ("Empfänger ist für dieses Konto nicht registriert."), an unconfigured channel or a dead gateway 503 ADAPTER_UNAVAILABLE with a specific reason — none of them leaves a draft behind (`native_approval_requests` stays empty, tested). The same holds on the command path: `services/messenger-action-intent.ts` parses German send/reply imperatives ("Schreib Anna über Telegram dass …", "Schick eine WhatsApp-Nachricht an … dass …", "Antworte auf ihre letzte Telegram-Nachricht dass …"); a phrase without channel context or message text is never a messenger action and falls through to mail/builtin/base handling. A spoken recipient resolves ONLY against the registered outbound targets (`messenger_outbound_targets`) by exact case-insensitive match on the stored platform recipient id — zero matches answer 404, a platform-only phrase with several registered targets answers 409, exactly one wins; a send to a guessed recipient is never staged. A spoken reply binds to the newest inbound observation (`messenger_sender_observations`, optionally platform-filtered); the observed chat must itself be a registered outbound target, otherwise the reply fails 404 before staging. The commands dispatch chain slots messenger BEFORE mail, because the mail compose pattern would otherwise swallow "Schreib Anna über Telegram dass …" as a mail recipient. Because the confirmation re-validates the draft and `confirm()` compares the exact stored action, a drifted registration between preview and confirmation fails 409 instead of sending to the wrong chat.

Web: `features/communication/MessengerCompose.tsx` sends plain messages through the shared `useRunStagedWrite` runner (first call stages, the shell `StagedWriteConfirmHost` repeats with `X-Action-Preview-Id`; no client idempotency key is sent for plain sends — the journal key derives from the preview id). The local preview group stays as the review step; the server preview is the binding confirmation. Escalation handoffs (`messengerNotification` URL parameter) keep the legacy direct confirm with their staged idempotency key, unchanged.
