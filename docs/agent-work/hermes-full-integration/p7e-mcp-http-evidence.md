# P7-E MCP HTTP checkpoint

The installed Hermes pin `d923a5eb487a17c0a68801bba9ef0f56c81040a8` keeps server definitions in `mcp_servers`. Its native [`mcp_config.py`](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/hermes_cli/mcp_config.py) `_save_mcp_server` validates entries and persists them; `_remove_mcp_server` removes them. The Friday bridge calls these functions via a bounded runtime child after pinned-source and revision checks. It never accepts a shell command, environment map or arbitrary config object on this route.

The owner can add, activate or remove a credential-free HTTPS server. Server URL validation rejects IP literals, local hosts, userinfo, query and fragment; existing entries with auth, tools or other keys are preserved and cannot be overwritten through this control. Status reads the complete configured `mcp_servers` map from the profile, exposes transport and an origin-only endpoint, and never reports a successful connection from a persisted write. A new Hermes session or explicit MCP reload is required for an already running agent to consume a change. Native stdio setup, OAuth/token setup and explicit network probing remain separate P7-E work.

Lifecycle checkpoint (2026-10-20): The owner can disable or re-enable an existing Friday-managed HTTPS entry without copying its URL into the browser. `mcp.activation` binds the write to the profile revision, reads the stored URL under the config lock, rejects entries with auth, headers or tool filters, calls pinned Hermes save logic, and checks persisted selection. It does not prove adoption by an existing session. The UI offers the toggle only on editable entries. MCP handshake, OAuth and runtime reload receipts remain open.

Protocol probe checkpoint (2026-10-20): The owner can explicitly probe one active Friday-managed HTTPS server selected by name and `If-Match` profile revision. A short-lived Python client resolves the configured hostname, rejects any non-global DNS answer, connects only to the selected numeric address, verifies TLS against the original hostname and uses the original HTTP Host. It follows no redirect and uses no environment proxy. The bounded [MCP 2025-03-26 Streamable HTTP](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports) handshake sends `initialize`, `notifications/initialized`, then `tools/list`; it never invokes a tool. Responses are capped at 64 KiB per protocol message. A result reports connection and listed tool count (with pagination completeness), never descriptions, server text, secrets or tool schemas. A new [2026 stateless protocol](https://modelcontextprotocol.io/specification/draft/changelog) is classified unsupported by this probe. `runtimeApplied:null` explicitly says no running Hermes session was inspected. This probes the protocol at the stored URL, not Hermes' broader native transport capabilities (OAuth, stdio, SSE fallback or live endpoint overlays).

The endpoint requires owner, CSRF and revision checks. A config edit during the handshake invalidates the receipt. Each POST opens a fresh TLS connection to the same pinned IP; this handles a server that leaves the prior SSE response open. Synthetic tests cover private DNS, a real local HTTP/1.1 TLS SSE keepalive round trip with three distinct pinned connections, bounded SSE, no redirect, no tool invocation, session ID binding and API access. The explicit Python CI list includes the TLS fixture and checks OpenSSL availability. Ubuntu bridge/protocol/updater tests: 27/27; focused Control API contract/route/service tests: 55/55; contracts check, typechecks, targeted lint and build passed. Live public server and Friday runtime tests remain NOT_RUN.

Bearer credential checkpoint (2026-10-20): A Friday owner can attach, rotate or remove a token on one existing managed HTTPS server. The PATCH body is write-only and bound to the profile's config-plus-`.env` revision; no token enters URL, CLI arguments, returned status or audit metadata. Hermes' pinned `_save_bearer_auth_token` writes its native `MCP_<NAME>_API_KEY` variable to the profile `.env`; config stores only `Authorization: Bearer ${...}`. The helper accepts only an exact managed server name and stored URL, rejects env-name collisions, existing foreign credentials, stdio/custom headers and unsafe URLs. Status exposes `authMode` and whether the profile `.env` has a value, never the value. Existing live Hermes adoption remains unverified; credentialed probes and OAuth consent are still open.

The two-file write is not atomic. Token setup saves the config template before the secret; removal deletes the secret before dropping the template. A failure can leave an unresolved template, which status shows and the owner can retry. The child checks the initial revision and native entry immediately before the config write, and checks the entry again before and after token publication. If an external writer changes the entry during publication, it removes only the exact newly written token when still present and reports an unconfirmed result; it never restores an unrelated config or credential. Concurrent third-party writers cannot participate in Friday's lock, so a timeout or conflicting write requires fresh status inspection. Synthetic tests inject failures after the first mutation and a foreign URL change. In clean Ubuntu, bridge/Bearer/HTTP/protocol/updater tests: 34/34; focused API route/service tests: 24/24; contracts check, API/web typechecks, targeted lint and app build passed. No live Friday profile was changed.

OAuth checkpoint (2026-10-20): For an active, Friday-managed HTTPS server without existing authentication, the owner can start a native Hermes SDK 2.0 authorization-code/PKCE login, poll its state, open the authorization URL and cancel before publication. The flow binds an unguessable ID to the Friday owner ID and config-plus-`.env` revision. Hermes `mcp==2.0.0`/`httpx2==2.12.0` are the pinned optional runtime; the fresh installer installs the MCP extra. The worker uses Hermes' `HermesProviderMixin`, callback handler, native DCR/client metadata and `HermesTokenStorage`, initially confined to a 0700 staging directory. It publishes `mcp_servers.<name>.auth: oauth` via Hermes' native `_save_mcp_server` and moves complete 0600 token/client/metadata files only if the original managed entry and revision still match. A failed publication rolls back only matching changes; a crash after the config write leaves an OAuth entry with no token file, which the UI offers to retry. Staged secrets are removed after the flow. Status exposes token-file presence, not token material, authentication success or running-session adoption.

Every worker HTTP request, including SDK discovery, DCR and token exchange, runs through a custom `httpx2.AsyncBaseTransport` that rejects non-HTTPS/non-public DNS answers and redirects, dials the checked numeric IP, verifies TLS against the original hostname, sends the original Host, disables environment proxies and caps request/response bytes. The explicit browser authorization URL is checked for a public DNS target before it is shown. A finite SSE `initialize` frame is accepted without waiting for stream EOF. An SDK 2.0 fixture exercises 401, discovery, DCR, PKCE challenge, token exchange and authorized retry through that transport, both with synthetic responses and with a local HTTP/1.1 TLS issuer. Tests also verify hostname/Host/IP pinning, redirect refusal, cancellation after the config write and preservation of a concurrent foreign config write. The worker never invokes MCP tools. `configured` means native config/token publication only; `runtimeApplied:null` remains truthful.

The terminal `configured` state is now written while holding the same profile config lock used by cancellation; a cancel before commit triggers rollback, while a cancel after commit observes `configured`. GNU `timeout` kills the whole runtime process group after 330 seconds even if SDK DNS or a socket read is stuck in a thread. Status verifies the worker PID and Linux process start identity, removes staged token material once that worker is confirmed dead, and marks an unfinished flow unconfirmed. A killed worker cannot publish later; its staged files stay mode 0600 only until the first status call or stale-flow cleanup.
