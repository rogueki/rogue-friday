# P7-F native cron write-lock gate

The pinned Hermes source `d923a5eb487a17c0a68801bba9ef0f56c81040a8` has `cron/jobs.py` SHA-256 `76ec76f0c3854c4ab23deb8a883633756dd8e3ca9223013af3edf658d2d41862`. Its `_jobs_lock()` degrades to a process-local lock after cross-process flock failure/timeout; concurrent gateway/CLI writes can then race. Friday's compare-and-mutate cannot be sound under that behavior.

`patch_hermes_cron_lock.py` admits only those exact original bytes or its own exact patched bytes backed by `.friday-cron-original`. It changes native writes to fail closed when cross-process locking is unavailable, and adds `friday_strict_jobs_lock()` for a bounded, non-degrading compare-and-mutate section. Unknown source bytes fail before changes. `--check`, `--require-patched` and `--rollback` are supported; rollback requires the original backup. Both clean installer paths apply the patch before Friday services start, Linux validation requires it, and both verified updater payloads include the patcher. Ordinary dashboard updates only carry files and do not patch a live Hermes process.

The isolated official-source test checks apply, idempotent verification, rollback, unknown-byte refusal, original file mode preservation, and the actual patched lock functions with failed/acquired flock. It executes the pinned `InProcessCronScheduler.start()` method with a failed first lock acquisition: the tick error is recorded, the heartbeat is unsuccessful, and the next tick proceeds without ending the loop. `test_hermes_cron_mutate.py` uses a disposable pinned source/profile and the actual native `create_job`, `update_job`, `pause_job`, `resume_job`, `trigger_job` and `remove_job`. Two concurrent OS processes submit the same store revision; exactly one writes, the other gets `store_revision_conflict`. No live Hermes profile was modified.

Friday's owner-only mutation route stages an exact action, binds confirmation to the saved request, and uses the existing persistent NativeApprovalRequests dispatch journal. A timeout or failed receipt is `uncertain` and is never blindly resent. The native helper checks source pin, patch, profile, timezone and store hash under the strict lock, then reads a bounded postcondition. `run` only confirms a next-tick schedule, never completed model execution. The fresh-install/runtime gate must still verify the real service manager and scheduler in the final Friday installation.
