# P9 mail action family slice

The mail mutation family (send / move / flag) now runs through the same native staged pipeline as the task and calendar families — no contract or OpenAPI change was needed. Direct API `POST /api/v1/integrations/mail/accounts/{accountId}/send` and `POST …/change` stage the exact write first: the initial request answers `403 APPROVAL_REQUIRED` with `stage: preview`, a `previewId` and a German `previewText`; the repeat must carry the unchanged action plus `X-Action-Preview-Id`. Under the captured tier-2 policy the confirmed request either returns `stage: approval` with an approval ID for the existing list/detail/decision UI, or executes once when approval is disabled. Guards run before anything is staged: an invalid send body answers 422, an unknown mailbox account 422 ("Mail Postfach existiert nicht."), a foreign sender alias 422, a missing SMTP secret ADAPTER_UNAVAILABLE, a move without destination 422 — none of them leaves a draft behind. `saveMailDraft` deliberately stays a one-shot idempotent append: a draft is a reversible mailbox object with its own message-id dedupe, not an irreversible external effect, and it was not named in the slice scope. Receipt review and archive reconciliation are unchanged read/repair paths.

Sends keep their at-most-once guarantee through the existing `mail_send_journal`: the journal key of a staged send is derived from the preview id (`native-action:<owner>:<previewId>` for direct confirms, `native-approval:<approvalId>` for the approval decision), so confirmation, approval and replay all land on the same durable reservation. A replayed send confirmation returns the stored receipt with `Idempotent-Replayed: true` and `replayed: true` without a second SMTP attempt; an uncertain SMTP outcome is answered as `uncertain` on every replay and never re-sent. `MailSendService` grew three seams for this: `checkedMailSend` (validate-only), `checkSendable` (account/alias/SMTP-secret validation without touching the journal, used pre-staging) and `outcomeFor` (journal state for a known receipt). `mail.change` has no journal of its own — the staged pipeline is its only at-most-once protection; a uidvalidity conflict at dispatch leaves the draft `uncertain` and a new draft is required, same as the calendar family.

The command path parses German mail intents in `services/mail-action-intent.ts`: composes with explicit subject ("Schreibe eine Mail an Max mit dem Betreff Projektstatus: …"), composes without subject ("Sende eine Mail an anna@example.test dass …", subject derived from the first body line, squashed, 60 chars) and replies ("Antworte auf die [letzte] Mail von Frau Becker dass …", "Antworte ihr: …"). A phrase without an actual message text is never treated as a mail action — "Sende eine E-Mail an Frau Becker" alone still falls through to the base command handler, which keeps the existing command-bar E2E untouched. Recipient names are resolved pre-staging against the INBOX senders of the chosen account (the default account, or the single configured one; otherwise 422 "Welches Mail Postfach…"): zero matches answer 404, several distinct addresses 409, exactly one wins; full addresses pass through unchanged. Replies bind to the newest matching mail: a named sender searches INBOX (ambiguous senders fail 409 pre-staging), no sender uses the single `mailbox:uid` of the command `context.selectedIds` or the newest INBOX mail overall. The Reply-To/From extraction, `Re:` prefix, `inReplyTo` and `references` chaining (with the 2000-char and message-id-format guards) mirror the voice reply path exactly. Because the confirmation re-resolves recipient and reply target and `confirm()` compares the exact stored action, a drifted mailbox between preview and confirmation fails 409 instead of sending to the wrong person.

`NativeExecutableAction` gained the `mail.send` / `mail.change` kinds in `services/native-approval-requests.ts` (receipt sentences "Mail <receiptId> versendet." / "Mail <mailbox>:<uid> aktualisiert."), plus a read-only `stateOf` accessor so a replayed confirmation is stamped as a replay. `handlers/approvals.ts` dispatches both kinds: sends go through the durable journal, changes through the account runner. Memory capture stays on the direct route path (`captureMailSend` with the journal key as event id, replay-safe via the existing dedupe); the approval-decision dispatch deliberately does not capture a second event. The dev scenario reset clears `native_approval_requests`, which covers staged mail drafts (tested).

Web: `features/communication/MailCompose.tsx` sends through the shared `useRunStagedWrite` runner instead of a one-shot POST with a client idempotency key. The local review group ("Versand prüfen" → exact message) stays; the server preview is the binding confirmation via the shell `StagedWriteConfirmHost`. The compose view stays open after execution and shows the receipt, the uncertain-review and archive-repair actions exactly as before — for that the `StagedWrite` contract grew an optional `onExecuted(response)` callback, invoked by both the runner and the confirm host. Draft saving is untouched (one-shot). The Himalaya compose page (`/communication/himalaya/send`) is a separate entry and was not touched.

Validation: baseline before the changes — the focused mail/command/approval files (`mail-accounts-routes`, `voice-mail`, `mail-bridge`, `approvals`, `native-approval-requests`, `native-task-action`, `native-calendar-action`) passed 51 tests. After the changes: new `mail-action-intent` suite 19/19 (11 distinct compose/reply phrasings plus 7 negative phrases and the derived-subject rules), new `native-mail-action` suite 9/9 (spoken compose through approval with exact-body 409 and single SMTP send, tier-2-off execute with journal replay, reply header binding to the newest sender mail, pre-staging 404/409 recipient failures without drafts, uncertain SMTP without resend, staged move with replay receipt, pre-staging 422 for unknown account and foreign sender, dev-reset consistency, mail content kept out of previews and the audit trail), the migrated `mail-accounts-routes` send test now drives the staged flow including tamper-409 and header/body replay. Web: new `MailCompose.test.tsx` 3/3 (staged send with identical body on both calls and receipt display, uncertain outcome with review action, pre-staging 422 keeps the dialog open). Full Control API suite: 96 files, 742 passed, 1 pre-existing skip, twice in a row (`--maxWorkers=4`; unrestricted parallel runs flake on this host regardless of the change — a clean-HEAD comparison run showed 33 files failing under load, so the worker cap was used for a stable signal); full web suite 72 files / 606 passed (`--maxWorkers=4`); API and web typechecks pass; ESLint on all changed files is clean; `git diff --check` is clean; no contract file touched, so `contracts:check` was not needed. Playwright on Windows against the real gated mock stack: `tests/e2e/command-bar.spec.ts` 6/6 and `tests/e2e/tasks.spec.ts` 4/4; no mail-specific E2E spec exists, so there was nothing to repair there.

Still unverified or out of scope: the approval-path dispatch does not write a durable-memory capture event (only the direct route does); a cross-owner replay of a preview id and a live restart during a mail dispatch remain unverified; `changeMailMessage` carries no Idempotency-Key in the contract, so only the staged draft protects it; account CRUD and OAuth routes stay one-shot; Hermes-side mail tooling (`mail-bridge`) stays read-only; the remaining P9 families (messaging, …) are untouched.
