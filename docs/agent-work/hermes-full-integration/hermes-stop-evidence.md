# Hermes `agents.stop` evidence

The current Friday Hermes adapter does not expose `agents.stop`: `adapters/hermes/src/manifest.ts` declares only `agents.read`, and `adapters/hermes/test/agents.test.ts` asserts that `stopAgent` is absent. This is a capability boundary, not evidence that the upstream endpoint does not exist.

There are two source references in this repository and they must not be conflated: the Hermes adapter mapping baseline is `0e427d788d253630d38a3a51cd76849e73cd6925`, while the config bridge's enforced `PINNED_SOURCE` is `d923a5eb487a17c0a68801bba9ef0f56c81040a8`. The official [`plugin_api.py` at the adapter mapping baseline](https://github.com/NousResearch/hermes-agent/blob/0e427d788d253630d38a3a51cd76849e73cd6925/plugins/kanban/dashboard/plugin_api.py#L3714-L3742) and at the [config bridge pin](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/plugins/kanban/dashboard/plugin_api.py#L3714-L3742) both contain `POST /runs/{run_id}/terminate`; it routes through `kanban_db.reclaim_task`, returns `{ok, run_id, task_id}`, and reports ended or non-reclaimable runs as conflicts. Thus the endpoint is present in both cited source snapshots.

This source check does not establish which Hermes build is installed or that Friday's configured dashboard accepts the route at runtime. The Friday adapter still has no stop implementation or live smoke evidence, so `agents.stop` remains unadvertised. Before enabling it, verify the deployed version and exercise the route against that instance; preserve the single-active-run guard and handle upstream conflicts as state races. Do not infer remote idempotency from Friday's local idempotency key.
