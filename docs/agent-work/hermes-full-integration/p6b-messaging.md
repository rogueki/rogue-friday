# P6b Messenger work, pinned Hermes v0.22.2

Source audited: `~/.hermes/hermes-agent` in Friday-Ubuntu at `d923a5eb`. This is a source inventory, not a claim of a live account connection. `gateway/config.py::Platform`, `plugins/platforms/*/plugin.yaml`, `tools/send_message_targets.py`, `tools/send_message_tool.py`, and `hermes_cli/send_cmd.py` determine the classification below.

The core enum has 23 entries and 21 bundled platform manifests; 11 names overlap, so the union has 33 entries. Six are internal ingress or relay (`local`, `api_server`, `webhook`, `msgraph_webhook`, `relay`, `wecom_callback`); two are protocol/coordination (`a2a`, `raft`); `email` belongs to the separately implemented mail domain. The 24 remaining messaging transports are:

| Current explicit outbound grammar | Still needs native typed setup/send validation |
| --- | --- |
| telegram, discord, whatsapp, slack, signal, matrix, mattermost, sms, irc, line, feishu, wecom, photon, buzz, ntfy | teams, google_chat, dingtalk, simplex, whatsapp_cloud, weixin, bluebubbles, qqbot, yuanbao |

The first column is only available when Hermes' pinned gateway config loader reports the transport enabled and configured. This does not prove network authentication or delivery. Telegram, Discord and WhatsApp already have distinct native setup/status or pairing from P6a; the other first-column providers still need native owner setup, runtime status, inbound identity admission and real account evidence. The second column is deliberately rejected by the Friday send API pending source-specific target grammar and setup; it is **not** counted as integrated. A few first-column syntaxes rely on the pinned Hermes adapter validating exact IDs after Friday's stricter admission. There is no directory name or fuzzy target lookup across accounts in Friday's API.

`GET /api/v1/messenger/catalog` reads each bundled `plugin.yaml` and the six built-in prerequisites through the pinned Hermes dependency runtime. It returns presence flags, Hermes configuration admission, and a PID-bound observed gateway state; it never returns credential values. The Settings catalog shows all 24 offered transports and distinguishes native setup availability from exact-target sending. A read-only probe against the actual pinned installation returned 24 offered entries, 0 configured entries on that profile, and no claimed connection. The catalog has no save/apply operation yet.

`GET/POST /api/v1/messenger/targets` and `DELETE /api/v1/messenger/targets/{id}` enroll exact owner/account/platform/recipient destinations independently of Hermes `*_ALLOWED_USERS`, which authorize **incoming senders**. `POST /preview` checks enrollment and Hermes config, then binds an owner-specific approval to account, transport, exact recipient, exact text, an opaque HMAC of effective Hermes platform config, and the random enrollment revision. `POST /confirm` rechecks these values, reserves a durable journal row before invoking `hermes send --to PLATFORM:exact-id --file - --json`, and sends text on stdin only. The fixed WSL bridge rechecks the approved config revision immediately before the CLI call. Concurrent confirms, replay and restart cannot send a second copy with the same reservation; an interrupted pending reservation becomes `uncertain`. Ambiguous CLI timeout or malformed/negative receipt is also `uncertain`, never a false `sent`.

No live message, paid call, gateway reconfiguration, login, QR scan, or external account proof was run.

Open before P6b acceptance: native typed setup/status for every remaining actionable transport, direct connector/auth checks, authenticated inbound sender-to-Friday identity links, channel-scoped Memory privacy policy before spooling, incoming dedup by account/provider event ID, safe outbound Memory context, and real external receive/send proof. A listed/configured transport alone is not a connected or delivered transport.
