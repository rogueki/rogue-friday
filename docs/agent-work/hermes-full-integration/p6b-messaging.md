`GET /api/v1/messenger/catalog` reads each bundled `plugin.yaml` and the six built-in prerequisites through the pinned Hermes dependency runtime. It returns presence flags, Hermes configuration admission, and a PID-bound observed gateway state; it never returns credential values. For the 21 transports outside the P6a Telegram/Discord/WhatsApp setup, `GET/PUT /api/v1/messenger/providers/{platform}` offers owner-only source-pinned fields. The `PUT` contract is a 21-way discriminated schema generated from the pinned manifests and six built-in prerequisite maps. Values travel in a CSRF-protected body, never in argv, result JSON or audit; the UI never prefills them. Broad `*_ALLOW_ALL_USERS` switches and unsafe filesystem selectors are excluded. The WSL helper uses the same `~/.hermes/.friday-config.lock` as the native config writer and compares an opaque HMAC revision over Hermes config and credential files. It invokes pinned `hermes_cli.credential_lifecycle` under the installed Hermes dependency runtime, checks `ok` and reads back `load_env()` after every operation. Multiline Google service-account JSON is parsed and canonicalized before the single-line credential write. A stale revision fails before invoking the credential writer. Failures after invocation are `partial` or `uncertain` rather than a false clean rejection. A save reports `gatewayRestarted:false`. `POST /api/v1/messenger/providers/{platform}/apply` is a separate owner/CSRF-protected action: with the same revision lock, it restarts the local Hermes gateway, checks systemd active state and reads PID-bound per-platform connection state. `applied` means the gateway restarted and remains active; the platform connection can still be `unknown` or `disconnected`. No apply was run against the real profile. Some connectors also require QR/account linking, callback registration or platform-specific external prerequisites; those are not satisfied by entering fields.

`GET/POST /api/v1/messenger/targets` and `DELETE /api/v1/messenger/targets/{id}` enroll exact owner/account/platform/recipient destinations independently of Hermes `*_ALLOWED_USERS`, which authorize **incoming senders**. `POST /preview` checks enrollment and Hermes config, then binds an owner-specific approval to account, transport, exact recipient, exact text, an opaque HMAC of effective Hermes platform config, and the random enrollment revision. `POST /confirm` rechecks these values, reserves a durable journal row before invoking `hermes send --to PLATFORM:exact-id --file - --json`, and sends text on stdin only. The fixed WSL bridge rechecks the approved config revision immediately before the CLI call. Concurrent confirms, replay and restart cannot send a second copy with the same reservation; an interrupted pending reservation becomes `uncertain`. Ambiguous CLI timeout or malformed/negative receipt is also `uncertain`, never a false `sent`.

## Gateway admission and identity integration

The pinned source `gateway/run_inbound_consumer.py` invokes `post_gateway_admission` only after gateway authorization, bot admission and session routing. Its payload includes `source.to_dict()`, platform, provider message ID, text and session key, but no reliable receiving bot account ID. Friday's plugin therefore accepts only the explicitly provisioned default account/profile and verifies the effective Hermes home with pinned `hermes_constants.get_hermes_home()`. A distinct 256-bit local bridge key can call only `POST /api/v1/integrations/messenger/events`; the Hermes CLI Memory key cannot. The installer provisions the key via stdin and a private WSL file after the pinned plugin is installed; no live provisioning was performed in this worktree.

Every admitted event is classified. Groups, unsupported profiles, private directives, detected credential text and disabled Memory policy are forwarded as metadata-only classifications with an empty text body; none enter the sender table or Memory spool. The Memory messenger channel defaults off and unknown channel names fail closed. Admitted private DMs create only sender/chat metadata until the owner explicitly links that exact platform, default-account and sender ID in Settings. A linked sender's event ID is derived from platform/profile/process epoch/sender/provider message ID; retries preserve the original timestamp and rely on the durable Memory event ID for deduplication. The Memory event retains a messenger channel and conversation scope. There is no separate inbound text outbox: if the local bridge fails, Hermes continues its agent turn and Friday has no captured Memory event. Non-default multiplexed profiles and receiving bot multi-account identities remain unsupported until the pinned hook supplies trustworthy account evidence.

The `default` label identifies the selected profile, not the receiving bot account. Therefore the hook now binds each observation, link, conversation and provider event ID to a key-protected random gateway-process epoch. Restarting the gateway changes the epoch and requires a newly admitted DM plus explicit owner relink, even when credentials are unchanged; this is a deliberate conservative limitation. A detected on-disk config/`.env` change during the running process is classified `account_changed` with empty text and suppresses capture until restart. The pinned gateway may multiplex named profiles under one process while its hook omits the receiving bot identity, so any named profile present also suppresses capture with `multi_profile_unknown`. The upstream hook still cannot prove a provider session change that happens entirely in-process outside those files; live account-change tests remain required.

The installer now carries `configure_messenger_inbound_bridge.py` and `setup_messenger_inbound_bridge.sh`; the first validates the pinned source and installed hook, writes `~/.hermes/friday-messenger-bridge.{key,json}` with private permissions, and restarts the gateway when an apply marker is missing or the configuration changed. It writes the digest-only marker after confirming systemd active, so a failed restart is retried on the next setup attempt. The Control API key is `dashboard/data/hermes-messenger-bridge/auth.key`; sender metadata/links/event IDs use the existing Dashboard SQLite DB, while captured Memory events use its existing Memory outbox. The provider credential writer additionally takes `.obsidian-vault.lock` after `.friday-config.lock` so Friday's Hermes `.env` writers serialize.
