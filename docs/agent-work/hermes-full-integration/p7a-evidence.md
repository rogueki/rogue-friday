Pinned Hermes source: `d923a5eb487a17c0a68801bba9ef0f56c81040a8` in Friday-Ubuntu. Read-only probe on 2026-10-19 returned 58 local skill manifests and 2 user-installed plugin manifests. These are installed manifests, not proof that their dependencies, credentials or runtime tools work. A different source revision stays readable but the P7-A fields become unwritable until reviewed against that revision.

The bridge invokes only `hermes config path`, `get <allowlisted-key> --json` and `set <allowlisted-key> <typed-value>` without a shell or `--force`. Hermes `hermes_cli/subcommands/config.py` defines those supported commands. `hermes_cli/config.py:set_config_value` writes a single raw user-config leaf through Hermes validation and preserves the other YAML keys; `get_config_value` resolves the effective config. Friday separately hashes `config.yaml` into a numeric `If-Match` revision. A profile-local bounded file lock serializes Friday bridge processes, with a fresh revision check while held. After Hermes writes, the bridge rereads raw metadata and effective values. A two-process fixture verifies that one of two writes with the same revision fails. External Hermes CLI processes do not honor Friday's lock, so this is not a global CAS guarantee; a final revision read detects changes before response, but concurrent external writes remain a limitation. The hash does not cover environment or managed-overlay changes. No provider secrets leave the bridge, and `model.api_key` reports only whether the config file has a value. Environment credential state remains unknown. The API requires an owner session, CSRF and `If-Match` for writes.
