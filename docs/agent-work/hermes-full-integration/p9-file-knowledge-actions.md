# P9 file/knowledge action family slice

The file/knowledge mutation family (memory create / update / confirm / delete / conflict-resolve, file rename / delete) now runs through the same native staged pipeline as the task, calendar, mail, messenger and agent families — no contract or OpenAPI change was needed. The previously port-backed pass-through routes `POST /api/v1/memory`, `PATCH /api/v1/memory/{id}`, `DELETE /api/v1/memory/{id}`, `POST /api/v1/memory/{id}/conflicts/{conflictId}/resolve` (the audit-note override in `handlers/domain-ops.ts` is superseded), `PATCH /api/v1/files/{id}` and `DELETE /api/v1/files/{id}` stage the exact write first: the initial request answers `403 APPROVAL_REQUIRED` with `stage: preview`, a `previewId` and a German `previewText`; the repeat must carry the unchanged body plus `X-Action-Preview-Id`. Under the captured tier-2 policy the confirmed request either returns `stage: approval` with an approval ID for the existing decision UI, or executes exactly once and returns the entity (memory, file, deletion `ActionResult`, or — for adapter-gated file deletions — the adapter's own `202` approval document). A replayed confirmation answers the stored receipt without a second port call: re-fetch for create/update/rename, a synthesized `ActionResult` from the stored draft for memory/file deletion, and the re-served adapter approval for a gated file deletion.

Guards run before anything is staged: unknown memories, conflicts or files fail 404; a stale `If-Match` fails 409 before staging (the staged draft pins the seen version and the port re-checks it at dispatch, so a replayed confirmation after a concurrent write fails 409 instead of applying over newer state); a locked memory refuses content changes and deletion 409; an already-resolved conflict and a locked replacement target fail 409; a rename target that is taken by a sibling in the same folder (case-insensitive) fails 409; invalid file names (path separators, reserved characters, trailing dot/space, only dots) fail 422 before staging; missing capabilities (`memory.write`/`memory.delete`/`memory.resolveConflict`, `files.rename`/`files.delete`) fail 403 `CAPABILITY_MISSING`. None of them leaves a draft behind (asserted against `native_approval_requests`). The confirmation binds the exact stored action: a tampered repeat body fails 409.

`NativeExecutableAction` gained the kinds `memory.create`, `memory.update` (id, pinned version, exact `MemoryUpdateRequest`), `memory.delete` (id, version, title), `memory.resolveConflict` (id, conflictId, version, exact body), `file.rename` (id, version, body, previousName for the audit trail) and the two file-deletion kinds `file.delete` / `file.delete.gated` in `services/native-approval-requests.ts`; the receipt sentences are `Gedaechtniseintrag <id> angelegt./aktualisiert./vergessen.`, `Konflikt <id> geloest.`, `Datei <id> umbenannt./geloescht.` and — deliberately honest for non-temporary files — `Datei-Loeschung <approvalId> zur Loeschung angemeldet.`. The gated/ungated classification mirrors the files port rule (small `temporary` files are removed immediately, everything else raises the adapter's own `delete_file` approval), so the staged sentence always matches what the adapter will actually do. `handlers/approvals.ts` dispatches all seven kinds on the decision's own idempotency key through one shared `dispatchKnowledgeAction` in `handlers/knowledge-actions.ts`, which the direct API handlers and the command path also use. The dev scenario reset clears staged knowledge drafts like every other family (tested: a confirmation after the reset fails 409).

The command path parses German file/knowledge intents in `services/knowledge-action-intent.ts`: memory creates ("Merke dir: <text>", "Speichere im Gedächtnis: <text>", "Erstelle einen Gedächtniseintrag: <text>", "Lege einen Eintrag an: <text>"), updates ("Aktualisiere/Ändere den (Gedächtnis-)Eintrag <ref> auf/zu <text>", "Aktualisiere den Eintrag <ref>: <text>"), confirms ("Bestätige den Eintrag <ref>"), deletes ("Lösche/Vergiss den Eintrag <ref>"), file renames ("Benenne die Datei <alt> um in <neu>", "Benenne die Datei <alt> in <neu> um") and file deletes ("Lösche die Datei <name>"). A phrase must visibly name the family ("Eintrag" or "Datei") — "Merkwürdig ist das" or "Erstelle eine Datei" are never knowledge actions and fall through to the other parsers. Spoken references resolve ONLY against the live registry: memory id, exact unique title (or exact content for title-less entries), or the single selected memory of the command context; files by id, exact unique name or single selection — zero matches 404, several 409, an action on a guessed reference is never staged. The parser slots into the dispatch chain between calendar and agent; dismissing the preview cancels the server draft, and confirmation/replay reads the stored draft, so a spoken delete replay works even though the entry is already gone.

Web: `features/memory/MemoryPage.tsx` (create), `features/memory/MemoryDrawer.tsx` (edit, confirm, pin, lock, forget, conflict resolution) and `features/files/RenameFileDialog.tsx` + `features/files/FilesPage.tsx` (rename, delete) run through the shared `useRunStagedWrite` runner — the server preview in the shell `StagedWriteConfirmHost` is the binding confirmation, replacing the former inline delete/replace confirm dialogs; If-Match, Idempotency-Key and body are captured in the send closure so a confirmation can never alter what was previewed. The gated file deletion still surfaces the adapter approval with its open-approval link after execution (202). The now-dead direct mutation hooks (`useCreateMemory`, `useUpdateMemory`, `useDeleteMemory`, `useResolveMemoryConflict`, `useRenameFile`, `useDeleteFile`) were removed from `lib/api/domains/{memory,files}.ts`. Component tests drive the staged flow (first call without, repeat with `X-Action-Preview-Id`, unchanged body/headers); the e2e memory spec confirms edit, pin/lock, forget, replace and dismiss against the rebuilt stack, each waiting for the server preview before anything executes.

Validation: new `knowledge-action-intent` suite 32/32 (19 phrasings across create/update/confirm/delete/rename/file-delete plus 13 negative phrases), new `native-knowledge-action` suite 10/10 (create with replay receipt and no duplicate, update with tamper-409 and version-drift 409 after a concurrent write, delete with stored-receipt replay, tier-2 approval exactly once with receipt sentences, pre-staging 404/409/CAPABILITY_MISSING without drafts, conflict resolve with guards and version binding, file rename with sibling-409 and replay, temporary-delete-immediately vs gated-delete-202 incl. adapter approval execution and its replay, spoken create/update/delete/rename through the command path with unknown-404 and ambiguous-409, dev-reset consistency). Migrated `contract`, `contract-gaps`, `mutations`, `realtime` and `sequence` suites drive the staged flow (direct writes in the realtime/sequence event tests run with tier-2 confirmations disabled for those fixtures). Full Control API suite: 102 files, 850 passed, 1 pre-existing skip (`--maxWorkers=2`). Full web suite: 72 files, 607 passed (`--maxWorkers=2`); API and web typechecks pass; ESLint on all changed files is clean; `pnpm contracts:check` passes (no contract file touched). `pnpm build:app` succeeds; Playwright against the rebuilt gated mock stack: `tests/e2e/memory.spec.ts` 11/11.

Still unverified or out of scope: real adapter semantics beyond the mock memory/files ports (the immediate-vs-gated delete classification and the 202 approval are the mock port's contract behavior; a real adapter that always deletes immediately would only make the `file.delete.gated` receipt sentence overly cautious); the adapter-level `delete_file` approval stays a second gate for non-temporary files with the mock adapter (the native pipeline is the first) — with tier-2 confirmations enabled a deletion therefore passes two human decisions; a deterministic version conflict at dispatch marks the native request `uncertain` exactly like a timeout (family semantics of the shared executor), so a drifted version needs a fresh preview instead of a retry; the approval-path dispatch writes no durable-memory capture event for the file/knowledge family (unlike mail/messenger sends); a live restart during a dispatch and a cross-owner replay of a preview id remain unverified like in the sibling families; spoken references match exact titles/content only (no fuzzy matching) and the memory create intent stores facts without entities or sensitivity labels; voice-command STOP semantics over staged knowledge drafts are STOP-03 work, not this slice.
