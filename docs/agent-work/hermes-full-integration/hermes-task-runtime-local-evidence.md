# Hermes task and agent lifecycle: local implementation evidence

Status: local source and fake-HTTP validation only. Friday's installed Hermes service was not changed or called.

## Upstream authority

The Hermes source snapshots `0e427d788d253630d38a3a51cd76849e73cd6925` and `d923a5eb487a17c0a68801bba9ef0f56c81040a8` have identical `hermes_cli/kanban_db.py` and `plugins/kanban/dashboard/plugin_api.py` bytes (SHA-256 in `installer/wsl/patch_hermes_run_stop.py`). The pinned source's `archive_task` changes a task to terminal `archived` in a transaction, closes its active run, then terminates the captured host-local worker after commit. The Friday guarded cancel keeps the write transaction open through the bounded worker kill and rolls back if that worker survives. The adapter calls only `POST /friday/tasks/{id}/cancel` after probing the patch; an unpatched Hermes cannot return false success.

Pin mapping: `docs/MAPPING/hermes.md` was researched against `0e427d7`; the existing Hermes config bridge and the fresh Friday installers use `d923a5e`. The two touched upstream files match byte-for-byte across these pins, so the same guarded patch covers both. The installer requires the `d923a5e` checkout, and the patcher independently requires the exact two source hashes; an unknown checkout or changed source fails closed. Both `installer/wsl/setup_hermes.sh` and `installer/install-friday-linux.sh` apply the patch before starting Friday services. The Windows dashboard updater's verified WSL payload carries both `setup_hermes.sh` and `patch_hermes_run_stop.py`; it does not silently patch a running Hermes during an ordinary dashboard update.

`retryTask` has no upstream idempotency on the original PATCH path. Friday only reopens archived tasks and blocked failures/Friday-stopped tasks through `POST /friday/tasks/{id}/retry`. The adapter sends the latest task event ID (the upstream revision), status, current run ID and claim lock from its detail read. The pinned handler checks all four inside the same SQLite write transaction as `archive_task`, `unblock_task`, or the archived-to-ready dashboard transition. A new run or any intervening task event yields 409 without changing that run. A `ready` task with a historical failure marker may already be claimed, so retry refuses it. The caller's `If-Match` still uses Hermes' derived timestamp version locally, but the server-side event/run/claim CAS fences the actual write. HTTP and registry retries are disabled for cancel/retry/stop even when Friday's key is present. A timeout after a write is an unknown outcome; the Control API's persistent owner-bound `native_approval_requests` row becomes `uncertain` and does not automatically dispatch again. Direct adapter callers need their own durable request journal.

The upstream `/runs/{run_id}/terminate` endpoint checks the named run, then calls `reclaim_task(task_id)` without binding the current claim. A newer run can start between these operations. The Friday patch introduces `friday_terminate_run` with a write-transaction check of `current_run_id`, active status and claim lock. It holds the write lock while blocking the task and terminating the captured worker, so a concurrent retry cannot release the task before the old worker stops. The pinned `_poll_worker_exit` polls 10 times at 0.5 seconds before SIGKILL; a worker blocked on a SQLite write during shutdown can therefore delay the stop by about five seconds, but cannot cause an unbounded grace wait. If termination fails, the transaction rolls back and the task remains running for reconciliation. A successfully stopped task remains blocked (`block_kind=friday_stopped`) until explicit retry. The adapter probes `GET /api/plugins/kanban/friday/run-stop-capability` before mutation and requires the patch marker. Unknown source bytes fail installation/validation. The patch keeps `.friday-original` copies; with Hermes services stopped, `python3 installer/wsl/patch_hermes_run_stop.py HERMES_PACKAGE_ROOT --rollback` restores the verified originals.
