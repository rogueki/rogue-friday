# P8 settings and dashboard action gap register

This source audit adds field-level evidence slots to `settings-runtime-map.csv` and action families to `dashboard-coverage.csv`; `dashboard-action-nlp-coverage.csv` expands the 20 areas into reviewable action families. `SOURCE` means a source path establishes a code/schema mapping only. It does not mean the behavior passed a test. `NOT_RUN` is retained for browser/runtime, effective readback, restart, failure recovery, accessibility and NLP acceptance. The read-only validator checks CSV structure only; it cannot establish runtime correctness.

The field matrix uses the exact 12 checks from `acceptance-ledger.md` (SETTINGS-ALL-04): source of choices; effective readback including pre-existing values; type/range/dependency validation; persistent save and write-only secret handling; actual apply/restart; domain-specific observed effect; restart persistence/effect; concurrent edit conflict; separate load/save/apply/verify errors; discard/compensation; keyboard/mobile/labels/help/loading/empty-list usability; and natural-language query/setup/change. A source citation records implementation mapping only; acceptance remains `NOT_RUN` unless separately evidenced. Existing 108 field rows and legacy columns remain intact.

Source corrections:

- `theme.activeThemeId`, `theme.cyanIntensity`, `theme.panelOpacity`, and `theme.goldIntensity` map to the live `AppSettingsProvider` apply effect in `apps/web/src/lib/settings.tsx` (`runtimeThemeSettings`, `applyTheme`). Browser style/readback and restart tests remain `NOT_RUN`.
- Orb fields map through `orbSettingsFromWire` in `apps/web/src/features/orb/OrbSlotInner.tsx`; motion mode also applies in `apps/web/src/lib/settings.tsx`. A static name miss was not treated as a missing consumer. Visual behavior tests remain `NOT_RUN`.

- `dataRetention.memoryDefaultTtlDays` is explicitly constrained to `null` by `SettingsService.assertReferences` and disabled in the UI; non-null expiry is intentionally unsupported.

Concrete local implementation gaps supported by source:

- Voice UI exposes `wakeWordEnabled`, `wakeWord`, `pushToTalkKey`, `speakerVerificationRequired`, `voiceHistoryEnabled`, `storeRawRecordings`, and `ttsRate`. The settings handler's explicit apply/rollback branch is limited to voice persona and input/output audio devices (`apps/control-api/src/handlers/settings.ts`, lines 315–364). No per-field update bridge/acknowledgement was found for the seven settings. These values can be persisted without evidence that the active voice service changes behavior.
- `voice.storeRawRecordings` is especially misleading: the settings UI permits true, while `adapters/voice-http/src/mapping.ts` reports `rawRecordingEnabled: false` and states the service never stores raw audio. The control should be explicitly unsupported/read-only or connected to an implemented storage behavior with accurate privacy disclosure; do not claim current recording behavior from the setting value.
- `voice.voiceHistoryEnabled` is likewise presented as editable while `adapters/voice-http/src/mapping.ts` hardcodes `voiceHistoryEnabled: true`. No handler gating of history reads/writes by this setting was found in the scoped source search. A local fix should either make the setting effective end-to-end or represent it as unsupported until that can be done.
- `voice.inputDeviceId` and `voice.outputDeviceId` do have apply/rollback and status acknowledgement code plus focused service tests. Physical device selection and audible/microphone effect remain hardware `NOT_RUN`; these are not classified as absent local consumers.
- Notification `channels[].accountId` accepts arbitrary text in `apps/web/src/features/settings/BasicAreas.tsx`; no selected-account catalog binding was found in the scoped control API path. A safe local task is to bind it to a verified account catalog or restrict it to the supported default value while preserving unknown existing values visibly.

## Action trace: Activity, Alerts, Approvals and Audit

The action CSV now traces 28 UI action families in these four areas from the callback or state transition to the API/local operation, and names the existing focused UI-test case. The tests are source references only; this documentation change did not execute them. Runtime/NLP acceptance remains `NOT_RUN`.

- **Activity**: `ActivityPage` filter state reaches `useActivityBuffer` and `useActivityStream`; older-page fetch is `GET /api/v1/activity` with cursor, and event detail is `GET /api/v1/activity/{id}` only when that event is not already buffered. Pause/resume, list/tree, autoscroll, reset, and correlation filter are client state operations. Task/agent jumps are client route navigation. Focused test cases cover filter conversion, pagination, pause/resume, autoscroll, tree/collapse, detail, and correlation at `apps/web/src/features/activity/activity.test.tsx:57-356`.
- **Alerts**: `AlertsPage` reads active/resolved lists via `GET /api/v1/notifications`; priority/category filtering and limit expansion are local query-state changes. `AlertItem`/`AlertDrawer` actions flow through `useAlertActions` to version-conditional `POST` acknowledge/snooze/resolve. P0/P1 resolve has an explicit confirmation step. Tests at `apps/web/src/features/alerts/alerts.test.tsx:106-231` cover the mutation calls, confirmation, source navigation, read-only capability and filters.
- **Approvals**: page filters/list use `GET /api/v1/approvals`; opening details uses `GET /api/v1/approvals/{id}` and receives the decision token. Approve/reject and request-context are distinct `POST`s; edit-before-approve adds `editedPreview` to the approve request, not a separate update operation. Linked task/agent/source callbacks only navigate. Tests at `apps/web/src/features/approvals/approvals.test.tsx:70-434` cover these flows, capability restrictions, approval token, reauth, and edit payload.
- **Audit**: list/detail/export use `GET /api/v1/audit/events`, `GET /api/v1/audit/events/{id}`, and `GET /api/v1/audit/export`. Hash-chain verification is local over the visible fetched entries and capability-gated; pagination increases the list limit. Tests at `apps/web/src/features/audit/audit.test.tsx:54-237` cover filters, details, chain logic, export and errors.

No Activity, notification, audit-query, or approval-decision NL intent was found in the searched `apps/control-api/src/services/command-intents.ts` and `apps/control-api/src/handlers/commands.ts`; corresponding matrix rows therefore state `NOT_MAPPED`, not an inferred parser name. Safe next implementation is a **read-only typed query provider** behind the existing command runtime, initially exposing only `activity.search/list`, `notifications.list/get`, `approvals.list/get`, and `audit.search/get`. Reuse the existing typed service/query boundaries and filter schemas, require the user's normal read capability, enforce bounded page sizes and explicit identifiers/date ranges, return redacted DTOs, and never expose the underlying HTTP client, DB, or arbitrary filter expressions to the model. Do not add approve/reject, notification acknowledge/snooze/resolve, or audit export as conversational actions in this read-only phase. Tests should prove the allowlist, identifier scoping, redaction and that no POST/DELETE is reachable.

**Settings and Content Studio follow-up**: settings rows remain governed by the exact 12-field acceptance matrix; for NLP, implement only read/query against effective settings with secret fields omitted or represented as configured/unconfigured. Do not route generic `settings.change` from a natural-language utterance until an explicit preview/confirmation path exists. Content Studio has real structured UI operations: `ContentStudioPage` loads the plan with `GET /api/v1/content-studio/plan`, saves via the plan persistence operation, and form handlers add/edit ideas and schedule postings; production workspace has separately typed generation/cancel/artifact operations. The current command-intent service has no Content Studio parser/consumer. The actionable NLP gap is therefore a bounded, read-only `content-studio.plan.list/get` provider first; generation, posting scheduling, key changes, and cancellation remain explicit UI operations pending a distinct confirmed command contract. The plan is account data, so the provider must scope access to the authenticated owner and redact provider credentials.
