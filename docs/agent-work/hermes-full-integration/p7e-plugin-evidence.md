# P7-E installed plugin activation checkpoint

The owner can activate or deactivate one already installed profile plugin. Friday takes `If-Match` and CSRF, checks its ID against the pinned `hermes plugins list --json --user` inventory under the profile config lock, rejects ambiguous/missing or catalog-removed rows, and calls Hermes' own `dashboard_set_agent_plugin_enabled` admission path with a bounded stdin-only helper. Hermes validates the active plugin dependency set before saving. Friday re-lists and reports the persisted selection; `applied` remains unknown because an existing gateway can retain handlers after disable or require restart. Source: [pinned plugin admission and activation](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/hermes_cli/plugins_cmd.py#L491), [pinned dashboard activation behavior](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/hermes_cli/plugins_cmd.py#L994), and [machine-readable installed list](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/hermes_cli/plugins_cmd_listing.py#L68).

This route never accepts a catalog install identifier, a repository URL, an executable, or a tool-override grant. Activation executes installed code at the owner's explicit action. The UI labels that action accordingly and does not claim runtime adoption from config readback. No live plugin was activated during validation.
